# Catalog and storage boundary

The first slice adds and lists products. Catalog is independent of Iced and storage representation. A product has a stable SQLite-generated integer identity, a trimmed nonempty name (at most 200 characters), an optional trimmed nonempty barcode (at most 100 characters), and a nonnegative price in integer centavos, bounded by `i64::MAX`. Barcodes are case-sensitive opaque strings; a nonempty barcode is unique. Blank barcode means absent. Prices are entered as decimal pesos with at most two fractional digits and converted without floating point. Products list by ID ascending.

The application operation accepts an owned draft and returns an owned product after commit, or a validation, duplicate-barcode, unavailable-storage or unexpected-storage error. Listing returns owned products or a storage error. A narrow catalog capability may be implemented locally and later by a remote application service; it exposes neither connections nor SQLite transaction objects. The operation owns validation and the atomic insert. This boundary alone does not solve authentication, retries after uncertain remote results, distributed consistency or multi-machine operation. Those require a later design.

The initial SQLite file lives in the current user's platform data directory under the application's name, on a local filesystem. One application instance is the intended writer. Open a connection for each blocking operation; set a bounded busy timeout, enable foreign keys, use WAL and synchronous FULL. SQLite controls serialization. Schema version is tracked with `PRAGMA user_version`; initialize the version and schema within one transaction, reject unknown newer versions and surface migration failures without resetting the database. The product table has integer primary key, name, nullable unique barcode and integer price; database constraints enforce nonempty values and nonnegative prices. Do not expose the file on a network filesystem.

Iced sends owned operation requests to a worker outside its GUI event loop and receives owned results as messages. While an add is in flight the submit control is disabled. Only a successful committed result is displayed as saved; preserve the form on failure. A lock, permission problem or full disk is an error, never a successful save. A termination before commit rolls back; after commit the product survives reopening, subject to filesystem and hardware durability. If a process dies after commit but before seeing the response, an operator must check the list before retrying: catalog adds have no durable idempotency key yet. Request identifiers prevent stale UI completions from replacing newer state, but do not make database writes idempotent.

Backup and restore need an SQLite-aware consistent snapshot and a tested off-machine encrypted copy before production. Fiscal state, sale intent, invoice authorization and archive obligations are separate later work. Comprobantes en Línea remains the current invoicing workflow; delayed fiscal issuance during a full outage is a known compliance gap.
